# TOE — The Opportunity Engine

A responsive four-tab web app for Career Fair 2026. Students describe what they have studied
and built; TOE ranks every opportunity on the fair floor against that profile using the same
retrieval-and-scoring pipeline as the [TOE-RAG Streamlit demo](https://toe-rag.streamlit.app/),
ported to TypeScript so the whole thing deploys to Vercel as one app.

## The four tabs

The tab bar is fixed to the bottom on every breakpoint: a full-width bar on phones, a centred
floating pill dock from tablet upwards.

| Tab          | Route       | What it does                                                                 |
| ------------ | ----------- | ---------------------------------------------------------------------------- |
| **Home**     | `/`         | How to use the app, career fair details, floor plan guidance, FAQs.           |
| **User**     | `/user`     | Student profile: degree, courses, skills, projects, interests, aspiration.    |
| **Results**  | `/results`  | Ranked opportunities with score breakdowns, retrieved evidence, AI explainer. |
| **Industry** | `/industry` | Exhibitor catalogue with search and sector filters, plus "Post an opportunity". |

## How the RAG pipeline is linked

A Streamlit app has no HTTP API — it is a stateful server-rendered session, so it cannot be
called from another front end. Rather than stand up a second Python service, the pipeline was
ported to TypeScript in `src/lib/rag/`:

- `tfidf.ts` — a port of `sklearn.feature_extraction.text.TfidfVectorizer` as the Streamlit app
  configures it (`stop_words="english"`, `ngram_range=(1, 2)`), including sklearn's exact
  tokeniser, its 318-word stop list, `smooth_idf` weighting and L2 normalisation.
- `engine.ts` — corpus construction, retrieval, and the weighted opportunity scoring.
- `context.ts` — the grounding context and prompt sent to DeepSeek.

**The port is verified against the original.** `scripts/parity.mts` and `scripts/parity.py` run
the TypeScript and scikit-learn implementations over the same corpus and profiles. All 42
retrieval and scoring values match to nine decimal places:

```bash
npm run rag:parity            # TypeScript output
python scripts/parity.py ../TOE-RAG   # scikit-learn reference
```

Matching runs entirely in the browser, so a student's profile never leaves their device.

### One deliberate change to the scoring

The original `score_opportunity` computes `occupation_fit` as the retrieval score of the single
best-retrieved occupation. That value does not depend on the opportunity being scored, so it is
**identical for every candidate** — visible in the live demo, where all three results report 19%
occupation fit. A 30%-weighted term that is constant across candidates shifts every score by the
same amount and cannot affect the ranking.

Here, each opportunity is instead linked to the O*NET occupation its work most resembles, and
`occupation_fit` asks how well the student matches *that* occupation. The similarity is divided
by `OCCUPATION_FIT_REFERENCE` (0.3) so the term spans a comparable 0–1 range to the other three
components without any candidate being guaranteed a perfect score.

The original behaviour is preserved and reachable — `rank(profile, { occupationFitMode: "legacy" })`
— and is what the parity test exercises. Weights are unchanged: required 35%, preferred 15%,
occupation 30%, career alignment 20%.

## Deployment

Deployed on Vercel. No environment variables are required — the app holds no secrets of its own.

## AI explanations

The ranking is deterministic and never touched by a model. The optional explanation on the
Results tab is generated by DeepSeek from the retrieved evidence.

Students paste **their own** DeepSeek API key. It is held in `sessionStorage` for that tab only,
discarded when the tab closes, and forwarded once per request through `/api/explain` to
`api.deepseek.com`. It is never logged, cached, or stored server-side. Proxying through the route
rather than calling DeepSeek from the browser keeps the request inside the app's own CSP.

## Security notes

- **Strict CSP**, no third-party origins: both typefaces are self-hosted by `next/font` and every
  icon is inline SVG, so the only connection the browser makes is back to the app's own origin.
  `frame-ancestors 'none'`, `object-src 'none'`, HSTS, `nosniff`, and a restrictive
  `Permissions-Policy` are set in `next.config.ts`.
- **Bounded, validated input.** Every profile field and company submission is parsed with Zod
  (`src/lib/schemas.ts`), length-capped, and stripped of control characters. The API route
  validates its body and rejects oversized requests.
- **Prompt-injection hardening.** Profile text and company submissions are untrusted input that
  ends up in an LLM prompt, so the evidence is fenced between markers, the fence itself is
  stripped from the data, and both the system and user prompts instruct the model to treat the
  block as data rather than instructions.
- **Rate limiting** on `/api/explain` (`src/lib/rate-limit.ts`). It is per-instance rather than
  global — enough to blunt scripted hammering of a route that spends the caller's own key. Swap
  in a shared store if it ever needs to be authoritative.
- **Upstream errors are mapped**, never echoed, so a DeepSeek response body cannot leak back to
  the client.

## Data

`src/data/occupations.json` (8 O*NET-aligned occupations) and `src/data/opportunities.json`
(12 roles). The three original opportunities and occupations from TOE-RAG are preserved with
their IDs; the rest are illustrative demo entries added to give the Industry catalogue something
to show. Companies, booth numbers and dates are not real.

Opportunities posted through the Industry tab are stored in `localStorage` for this demo, so they
are visible only on the device that submitted them. They are added to the corpus immediately and
scored alongside the catalogue. Moving to shared persistence means swapping that store for a
database — the rest of the pipeline is unaffected.
